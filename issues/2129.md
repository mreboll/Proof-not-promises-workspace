# #2129: Feature Request: Allow generation of Formatter for a type in a referenced assembly

Fuente: https://github.com/MessagePack-CSharp/MessagePack-CSharp/issues/2129

## Is your feature request related to a problem? Please describe.

Given the following project structure:

 - Project A
    - `ProjectA.MyType`

 - Project B
    - References
        - Project A
    - Package References
        - MessagePack
    
I need to have a source-generated `IMessagePackFormatter` for type `ProjectA.MyType` generated **inside Project B** instead of Project A, because the latter has no (and cannot have) reference to MessagePack nuget package.

## Describe the solution you'd like

Add a `[GeneratedMessagePackFormatter]` attribute that will work for partial classes implementing `IMessagePackFormatter<T>`.

For example:

```csharp
[GeneratedMessagePackFormatter]
partial class MyObjectFormatter: IMessagePackFormatter<MyObject>;
```

That's it. The class does not even need to declare a body (no `{` and `}`), because the actual implementation is source-generated by `MessagePack.SourceGenerator.MessagePackGenerator` as usual.

As for the attribute-based property keys and other settings (such as Union), I can think of 3 alternatives:

1 - Use `System.Runtime.Serialization.DataMember` and related attributes. This is too limited IMO, as it cannot have `Union` and other features.

2 - Allow the generator and analyzers to work with user-defined versions of the MessagePack attributes. This would be similar to how you can declare dummy versions of BCL attributes that the C# compiler expects, such as [`[IsExternalInit]`](https://stackoverflow.com/a/67687186/643085) or `[ModuleInitializer]`. With this, I could simply copy and paste the attribute definitions for MessagePack attributes such as `[Key]` into my Project A, and have the source-generated formatter (as described above) pick them.

3 - Source-generate the attributes themselves using [`IncrementalGeneratorInitializationContext.RegisterPostInitializationOutput`](https://github.com/dotnet/roslyn/blob/main/docs/features/incremental-generators.md#outputting-values) instead of them existing in the `MessagePack.Annotations` assembly. This would allow using the attributes without adding an additional runtime dependency. Only compile-time reference to the analyzer Nuget would be required.

## Motivation

Project A is really a library (Nuget package), and I really want to keep it minimal. It currently has zero dependencies and I would really like to keep it that way.

### @AArnott

Hey @dotfede. Thank you for the proposal and the offer to help. That's awesome. 

Does ProjectA.MyType requires only `public` members to be serialized? That seems a prerequisite for anything here.

I think your example here is excellent:

```cs
[GeneratedMessagePackFormatter]
partial class MyObjectFormatter: IMessagePackFormatter<MyObject>;
```

We might simplistically say this only works in "contractless" mode, such that you need no attributes on it at all. If there are attributes on it, fine, we'll use them. But if there is no `[DataContract]` or `[MessagePackObject]` attribute on the type, go contractless by default. That sounds like it ought to work most of the time, and save you the trouble of defining extra attributes using any of your 3 options for it.

I am _not_ a fan of the last idea, of defining some `PropertyKeys` dictionary to pseudo-write the formatter. If you're going to do that at all, I'd say just write the formatter -- it's not that hard.

As for the attributes working in ProjectA without a dependency, that works for compile-time only features such as the C# compiler itself and attributes that serve as source generator inputs. But it falls down when these attributes are reflected over at runtime and expected to have some type equivalence. MessagePack-CSharp has dynamic resolvers that _do_ in fact use reflection on these attributes and execute the attributes to get at their values. So if an assembly defines its own copy of these attributes, they won't be seen (at best) or they'll cause InvalidCastExceptions (at worst). This could be resolved by using _more_ reflection and very carefully so. And if we went that route we should add tests to ensure it works properly. 
So that's all to say, I wouldn't run into the attributes if you can avoid it.

In fact, speaking of 'contractless', have you considered writing your own _resolver_ that checks specifically for any `ProjectA` type and engaging the Contractless dynamic resolver in those cases? That's just a few lines of code. No new feature required.

### @AArnott

> Yeah not the most elegant solution... What about something like:

Better, I guess. But I can't quit thinking there's a simpler way. Something like [surrogate types](https://aarnott.github.io/Nerdbank.MessagePack/docs/surrogate-types.html). Suppose for example you had something in your library as simple as:

```cs
record ProjectASurrogate([Key(0)] int Property1, [Key(1)] string Property2);
```

And then we went with your idea of a source generated formatter, but with a twist:

```
[GeneratedMessagePackFormatter(SurrogateType = typeof(ProjectASurrogate)]
partial class MyObjectFormatter: IMessagePackFormatter<MyObject>;
```

The source generated formatter would then use key indexes based on the surrogate by mapping them to the original via matching property name of the original type from your SDK. That way any sort of attribute could theoretically be described. The surrogate type itself in this design wouldn't actually be used at runtime. It's just a basis for the source generator to see what to do.

>  Of course this is hard to maintain because it implies that whenever SDK types change I need to also change the source-generated-but-not-quite formatters.

In a world where the original type is not attributed _and_ you want to apply key attributes, I don't see any alternative. You'll have to adjust the indexes or define new indexes for new properties as they are added anyway. 
Unless you don't care about serialized data format compatibility with older/newer versions, in which case the indexes assigned can be arbitrary. At that point, if a feature existed that automatically assigns keys, then we could imagine a better world.

>> But it falls down when these attributes are reflected over at runtime and expected to have some type equivalence

> I would think this isn't happening in my current setup? Otherwise I'd get runtime exceptions because SDK types have no attributes at all.

Your current setup involves source generated formatters, so you're not using the reflection-over-attributes route and therefore need no attributes (at runtime) at all. But if we claim to support that folks can just copy the attributes from the library into their own projects, that'll currently work _only_ if they are using source generation (or _could_ work at least if we make sure our source generator doesn't care where the attributes are defined).
But it'll fall over in the reflection mode of the library, in a very confusing way. So I'm not a fan of going that route.
