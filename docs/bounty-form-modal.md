# Bounty form: Best use of Modal

Text ready to paste into the Junction 2026 submission form. Every number comes from a real run in this
repository (`docs/numeros-evidencia.md`, `fixtures/bench_2283.json`, `fixtures/report_2283_modal.json`).

---

**Project:** tieto-ledger, a Risk-Scoped Evidence Ledger (Tieto challenge "Earned Trust in AI Code").

**One sentence:** we never let an AI approve code by argument, only by tests that run — and every test or
mutant an AI writes is untrusted code, so it runs in a disposable Modal Sandbox with no network.

**Why Modal is central.** Our pipeline makes AI models write executable evidence: a change test written from
the issue alone, Defender tests that answer each objection, and mutants that break each edge case on purpose.
That is code generated by a model and executed against a real C# repository. Running it on a developer's laptop
contradicts the whole idea of earned trust. `ModalTestRunner` implements the same `TestRunner` interface as the
local runner, so switching is one variable: `LEDGER_RUNNER=modal`.

**How we use Modal.**
1. **Image as the trusted baseline.** `mcr.microsoft.com/dotnet/sdk:8.0` with the challenge repository cloned and
   the base and PR worktrees of all four issues already restored and compiled (8 builds). Every package the tests
   need, including the reference assemblies they download at run time, is fetched while building the image.
2. **One Sandbox per run, `block_network=True`.** Each test or mutant runs in its own container with no network;
   the AI-written code cannot exfiltrate anything or pull dependencies. A mutant is applied directly inside its
   sandbox, which is thrown away afterwards: no shared state between base, PR and mutants.
3. **Parallelism.** Base, PR and mutant run at the same time in three sandboxes.
4. **Guard rails.** Everything that ends up in a sandbox shell command is validated before any sandbox is created
   (issue id, test class name, mutant patch limited to existing `src/**/*.cs` files). Every sandbox is terminated
   in a `finally`, and an infrastructure failure is recorded as "no evidence", never as a pass.

**Measured results.**
- **Base + PR + mutant on #2283: 28 s in parallel on Modal vs 63 s sequential on the laptop, identical results**
  (base red, PR green, mutant red). Reproducible with `python -m ledger.evidence.bench --issue 2283`.
- **Full pipeline for #2283 (triage, change test, invariance, cross-examination with mutants): 11 min on Modal vs
  18–22 min locally.** Two of three Prosecutor objections were validated against their mutants; the third test was
  rejected because it also passed against the mutant.
- Image build: 5.5 min once, cached afterwards.
- **Total cost of everything we ran on Modal during the hackathon: $0.21 in credits, $0 in charges**, with a usage
  limit equal to the free monthly credits.

**What Modal taught us (real failures, from our lessons log).**
- In a sandbox with no network, an AI test that downloads packages at run time fails — and that failure looked
  exactly like "bug reproduced" on the base branch. We now mark network and package-download failures as `INFRA`
  so they can never count as evidence, and the image pre-downloads those packages. Running untrusted code
  isolated is what exposed a false positive in our own verifier.
- Our first retry for applying a mutant patch was chained so that the fallback always ran and failed; the first
  real sandbox run caught it.

**Honest limits.** The generation-invariance check (our differential oracle) still runs locally; what goes to
Modal is all the code written by AI. The cross-examination loop is sequential per objection, so the full-pipeline
speed-up comes mostly from faster, isolated builds rather than parallelism.
